# WTRAVEL 航向异常检查（2026-10-11）

## 确认的缺陷与修复

`BasicMotionNode._step_move_world` 曾直接用 `目标yaw - 实测yaw` 拆分步进。
当实测为179°、目标为-179°，正确误差是+2°，旧实现得到-358°。
如果剩两步，首步会给出-179°增量，中间目标可能转到0°。
MCU最终目标角的归一化无法修复这个已经错误生成的中间目标。

另一个问题是差值以实测姿态为基准，而 `set_step` 将增量叠加在上一条
目标姿态上。例如目标已为90°、实测仍为80°，旧逻辑继续向目标叠加正角度，
使前进阶段本应固定的航向发生偏移；最终定位又恢复原目标，可能表现为转动或摆动。

修复为 `wrap_deg(目标yaw - 上一次目标yaw)` 后再拆分。
因此跨边界走最短角度，已经下发的行进航向不会因控制滞后而被重复修正。
同时修正WTRAVEL日志的方向角：按实测位置计算，避免旧目标位置误导排查。
修复也覆盖共享步进函数的WMOVE/BMOVE。

## 其他检查结果

- BasicMotion到MCU保持度转弧度；没有发现±π两侧固定极性反转。
- MCU `MotionContext::wrapAngle`、位置环角度误差和角度规划目标已做归一化。
- WTRAVEL有水平行程时先朝向航行方向，结束时保持该方向；配置yaw由海参任务
  后续SET恢复。这是当前调用约定，没有在本次修复中改变。
- 恰好相差180°时两种旋转方向等长；本修复不增加固定转向策略。

## 验证与现场复核

控制包25项测试通过，新增测试调用实际步进规划及 `set_step` 方法，覆盖正反跨界、
±180°等价、超出规范范围的目标和实测航向滞后；不发送真机指令。
20261010_180812旧会话有34条步进向量日志，最大yaw增量约2.08°，
没有直接记录本次边界故障，不能据此确认现场乱转的唯一原因。

更新运行环境并重启basic_motion后，记录往返经过±180°的WTRAVEL。
对照 `/basic_motion/pose` 的robot_yaw/target_yaw、`/zit6/cmd/setpoint` 的yaw、
`/zit6/state/pos` 和角速度，区分上位目标跳变、其他发布者覆盖指令与底层跟踪异常。
