## 1. 先看实际会跑什么

### 1.1 当前 mission 并不是完整比赛流水线

`workspace_auv/src/uv_task/config/missions/robocup_26.yaml` 的有效顺序是：

```text
start
  → 26rb_grab_ball_ring
  → 26rb_drop_ball_target_rack
  → return_origin
```

撞球整段被注释。过门整段也被注释，而且其文本位置在放球任务之后。即使把两个注释块直接取消注释，也会得到“启动→撞球→抓取→放球→过门→返航”，仍不是用户指定的“启动→撞球→过门→抓取→投放→返航”。当前只抓 `pink_golf`，撞球 order 只配置蓝球；不是自动抓两色球、撞两色球、过四门。

要形成用户描述的完整流水线，需要在 mission 中明确启用并排列六个任务；本报告不擅自将此改为实车行为。过四门还需把 `gate_count` 和四个 `observation.poses` 一起配置，不能只改 `gate_count`。

### 1.2 当前所有 mission 入口/返航坐标

| 所属任务 | 顺序 | 命令/axes | target [x,y,z,yaw] | 真正含义与时限 |
|---|---:|---|---|---|
| start | 1 | BMOVE/xyzrz | [0,0,0,0] | runner 特判跳过，先 START 建原点；不是先移动到零点 |
| 抓球环 | 1 | SET/z | [1,0,0.2,0] | 只有 z 生效，x=1 不参与移动；单条默认 60s |
| 抓球环 | 2 | WTRAVEL/xyz | [1,-1,0.2,0] | odom 绝对位置，先朝行进方向再步进；单条默认 60s |
| 抓球环 | 3 | WTRAVEL/xyz | [2,-1,0.2,0] | 同上；yaw=0 不保证最终朝 0°，正常行进用 atan2 方向 |
| 投放 | 1 | BMOVE/xyzrz | [0,0,0,0] | 以实测位置为起点的零偏移步进/保持；不是返回世界原点；60s |
| 返航 | 1 | WTRAVEL/xyz | [3,-1,0.2,0] | 先到世界中间点；60s |
| 返航 | 2 | WTRAVEL/xy | [0,0,0.2,0] | 回 odom XY 原点；z 字段被 axes 排除，保持动作接收时的实测深度；60s |
| 返航 | 3 | SET/rz | [0,0,0,0] | 只设置航向 0°；不是同时 z=0；60s |
| 返航任务体 | 4 | BODY_VELOCITY | vz=-0.05 | 按起始 z 算时间，开环上浮估算至 -0.3m；30s 参数约束 |

被注释的撞球入口：`SET/xz [0.5,0,0.2,0]` → `WTRAVEL/xyz [4,-1.8,0.2,89.9544]` → `SET/rz ...89.9544`。`89.9544°≈1.57rad`；任务接口接收的是度数。被注释的过门入口：`SET/z ...0.2` → `WTRAVEL/xyz [1.5,-2,0.2,0]` → `SET/rz ...0`。过门任务体本身还会再次 BTRAVEL 到观测点再 SET 完整观测位姿，因此重新启用时存在重复到点/保持动作。

证据：`task_runner.py:680 _execute_initial_pose`、`896 _send_action_goal`、`1232 _task_return_origin`；`basic_motion.py:1271 _travel_world`、`1543 _execute_motion`。

### 1.3 任务失败后不是自动中止全局 mission

`run_task_list()` 无论一个任务返回失败还是抛异常，只要 `stopped` 没置位，都执行 `current_index += 1`，继续下一个任务。`on_failure` 不是重试指令，也不是跳转地址：它只给紧接着的一个任务覆盖参数/初始位姿，之后清空。当前 `{}` 失败钩子不改变任何参数或位姿，没有自动“重来一次”。无匹配失败钩子也照样继续下一任务。

只要任何任务记录过失败，最终 mission 状态是 ERROR；后面的任务成功不会清掉历史失败。列表走完的日志不代表全链条成功。停止时状态是 PAUSED。任务开始时会清本任务的 `_last_motion_failure_kind`，因此不能把某个内部失败始终期待为 `.timeout`。

当前失败钩子只含：`start.timeout`、`26rb_grab_ball_ring.both_exhausted`、`26rb_drop_ball_target_rack.timeout`、`return_origin.timeout`；都为空。球环只有一项失败时的 `.golf_exhausted`、`.ring_exhausted`，以及搜索失败、恢复失败，并没有专属覆盖，但仍进入投放。投放也不读取 pickup 成功标志，可能在没抓到物品时照样发释放指令。

全局层面“旧动作未确认禁止继续”也不完整：过门和搜索局部禁止启动其后运动，但 runner 本身没有把这类失败转换为 `stopped=True`；返回失败后仍可能进入下一任务。这是局部保护与全局推进策略的差别。

证据：`task_runner.py:737 run_task_list`；`mission_policy.py`；`26rb_drop_ball_target_rack.py:391 execute`。

## 2. 坐标、深度、速度和观测的共同约定

### 2.1 几种深度一定分开

| 名称 | 当前数值 | 用途 | 不应混淆为 |
|---|---|---|---|
| 作业/巡游深度 | 常见 0.2 | 机器人 base/odom z 目标 | 夹爪末端深度 |
| collection_frame_position.z | 0.5 | 预设物体位置描述；搜索实际只用其 XY | 搜索自动下到 0.5 |
| rack_position.z | -1.0 | 预设描述，投放搜索只用其 XY | 机器人上浮到 -1.0 |
| golf/ring.grab_depth_m | 首次 0.44 | 机器人 odom z 下潜终点 | 物体自身 z、离框高度或夹爪深度 |
| 返航 ascent_target_z_m | -0.3 | 开环上浮时间的估算目标 | 测得到达水面或已上锁 |

组合抓取明确把所有搜索和水平修正定深到 `work_depth_m=0.2`；球、环分别使用 0.44、0.49、0.54 的三次目标，恢复用 `SET/z→0.2`，不使用旧固定时间上浮。过门深度来自本门 `observation.poses[i][2]`，不是默认为 0.1 的兼容 `depth.front`。投放先定深 0.2，但搜索后水平伺服第一次读取实测 z 并锁定这个值，随后两只爪共用；并未直接把 `_servo_depth` 强制赋为参数 0.2。

### 2.2 命令的实际语义

| 命令 | 目标语义 | 运动方法 | 是否在任务层设定匀速 |
|---|---|---|---|
| SET | odom 绝对 [x,y,z,yaw] | 一次位置目标，等待误差进入容差 | 否；速度由 MCU 位置控制和限幅决定 |
| WMOVE | 实现中是 odom 绝对终点 | 椭圆步长分段位置目标 | 否 |
| BMOVE | 以动作接收时实测位置/航向为基准的 body 偏移 | 转成 odom，分段位置控制 | 否 |
| WTRAVEL | odom 绝对终点 | 先转向目标 XY 方向，再步进到点 | 否 |
| BTRAVEL | body 相对位移 | 先换算终点，再走 TRAVEL | 否 |
| BLINE | 冻结起点及 body 相对位移形成有限 odom 线段 | ALIGN→CAPTURE/CRUISE/BRAKE→TERMINAL→HOLD | 有巡航速度上限，但有加减速、横向修正及保持 |
| BODY_VELOCITY | [vx,vy,vz,yaw_rate] 为机体系 | 短租约速度，立即完成 action；需周期续发 | 是；yaw_rate 进协议前转为 rad/s |

接口文件中 WMOVE/WTRAVEL 的注释曾写成 dx/dy/dz，与 Python 实现和当前 mission 使用的绝对目标有冲突，审查以实际派发为准。`BMOVE` 的 axes 在 `_execute_motion` 的对应派发分支未逐轴屏蔽，而是四个目标值全传入；现在球爪平移其他值都为 0，因此不发生额外 dz/dyaw，但不能依赖 axes 排除任意非零字段。

位置动作默认到达判据：机体误差 `|x|≤0.1`、`|y|≤0.1`、`|z|≤0.1m`、`|yaw|≤5°`；无“持续稳定 n 秒”要求，也无速度到零判据。只选 z 的 SET 仍会等待动作接收时固定的其他轴误差满足 `_wait_reached`。这些容差明显宽于视觉伺服要求的 0.03m 深度容差。

位置步进：STEP_X=0.6m，STEP_Y=0.4m；基础步长 `1/sqrt((cosθ/0.6)^2+(sinθ/0.4)^2)`，乘 `exp(-2|e_lateral|)`；STEP_PERIOD=0.2s；等到最后一段再直接定位。不能从 0.6m 步长或 0.2s 阈值算出 3m/s 的实艇速度。

### 2.3 BLINE 的隐藏控制参数

默认 `line.default_speed=0.15`；API 只允许显式 `0<cruise_speed<0.18`，0 代表使用默认值，0.18 会拒绝。`line.max_speed=0.25` 是合速度限幅，不是允许任务把巡航速度设为 0.25。

加速 0.05、减速 0.05、合速度变化率 0.05、制动模型加速度 0.03m/s²；横向增益 0.5，横向修正上限 0.10；横差>0.30m 进 CAPTURE，≤0.15m 退出，捕获沿线速度≤0.05；反向≤0.05；终端合速度≤0.08；距终点≤0.20m 或已越过终点进入 TERMINAL。刹车距离根据实测/指令速度加上 0.25s 延迟估算。

终点：每个世界轴误差≤0.10m、世界合速度≤0.03m/s、航向≤5°，连续 HOLD 满1s才成功。ALIGN 最多30s，还要求靠近冻结起点、航向达标、速度够低。BLINE 循环每0.05s，单次调度间隔>0.25s会中止，旧速度租约会停止。没有显式 timeout 时，动作上限 `max(60,L/speed+50)`；本链条多数显式配置动作时限。

BLINE 的“0.15m/s×8秒=1.2m”只是匀速理想距离；撞球八秒从第一次实测沿线正速度反馈开始算，其中仍有加速段，不保证实际前移1.2m。0.5m approach 和1.6m穿门还包括减速/终端/HOLD，不能把 L/v 当总耗时。

证据：`uv_control/config/default.yaml`；`uv_control/uv_control/line_guidance.py`；`basic_motion.py:1365 _execute_body_line`。

### 2.4 观测不是一个统一超时

- 前视撞球：消息接收年龄≤5s，同时非零 header stamp 与 ROS now 的绝对差≤5s，并对非零capture_id去重；空检测立即使该目 latest 无效。每个观察/对准阶段需要进入阶段后的新 sequence。
- 前视/下视搜索：0.8s；搜索独立订阅，检查 header stamp 和重复 capture_id；下视首次发现会锁存见到时间，后续0.5s里即使丢失也可能结束巡游，交给后续重新观测判定。
- 过门：1.5s；bbox 至少12像素、置信度≥0.02；三帧身份确认；失去主目2s才释放所有权，重获最多10s。
- 抓取/投放下视：相机所有权3s固定租约；每条新回调争抢，丢目标/过期即释放，不能靠另一个眼缓存直接接管；切目时重新累计居中保持。
- 抓取/投放 `pixel_tolerance_fraction` 实际比较去内参/去畸变后的 `du,dv`，基本是光学归一化坐标（约 Δu/fx、Δv/fy），不是直接按全画幅百分比。0.02 不等于1280像素宽的2%；真实下视中心附近约23像素，仿真下视约13.4像素。
- 主 runner 下视缓存回调未单独检查 header 年龄或 capture_id 去重，只检查几何绑定后按接收时刻入队。因此下视伺服及复检的“新鲜”主要是回调接收新鲜，不能自动证明传感器采集新鲜；与搜索独立订阅的校验强度不同。
- `_latest_robot_pose(require_measured=True)` 只拒绝没有实测值，不检查实测值多久以前收到；basic_motion 的1s状态门禁是另一层保护，不等于任务侧几何绝无陈旧姿态。


## 3. 启动与到目标点：逐动作、逐失败路径

### 3.1 任务节点能否启动

`task_runner` 构造时最多等 BasicMotion server 5s，没找到先记录错误。主函数随后等 `/auv/perception/model_classes` 10s；没有映射直接退出2，不执行任何 mission。非调试模式加载并严格验证 mission；配置错误同样退出2。`debug_mode=true` 跳过自动启动，等 execute 服务。`auto_start=true` 是 task launch 默认值；debug模式优先。`real_test_runner.yaml` 明确配置 `debug_mode:true`，是否生效取决于是否实际作为 params_file 传入。

当前真机 `real.launch.py profile:=task` 是准备系统依赖，profile 注释和实现均指向“task_runner单独启动”，不是一启动这个 profile 就比赛出发。相机默认 profile=default 时 `enable_camera:false`；task/debug 才打开。当前 enable_nav=false，26rb 任务直接调 basic_motion，没有走导航规划/避障路径。

### 3.2 start 准备灯光与 START

| 步骤 | 实际等待/动作 | 可被回车跳过 | 失败/边界 |
|---|---|---|---|
| 准备 | 黄灯1s | 是 | `_sleep_or_skip` 检测 stop/skip |
| 提示拔缆 | 0.5s灭 +0.5s红，共1轮 | 是 | 没有真正读取拔缆传感器或服务确认 |
| 绿灯倒计时 | 7轮，每轮0.25s灭+0.25s绿，共3.5s | 是 | 日志“6秒后启动”与这一段实际3.5s不一致 |
| 最后等待 | 1s+绿灯1s，共2s | 是 | 正常准备总计约7.5s，不计日志/调度 |
| START action | target零，timeout=0 | 之前回车直接到此 | 特殊超时规则见下 |

START 控制层先关 ARM 心跳并中性速度，等之前运动释放、收到新鲜未解锁 MCU 状态；请求 MCU 原点重置，等匹配 reset result 及新的 odom origin_generation，再打开 ARM 心跳并等已解锁确认。前段共享默认10s截止；解锁确认另外20s，故 `timeout=0` 的 START 不是普通60s，也不保证整段严格10s。近似上界为前段10+解锁20s，外加传输等待/调度。任一步取消、safe-stop、导航重启、原点错代、新鲜状态不满足都失败并停心跳。

成功后 runner 指令位姿清零并 `reset_pickup(start_xy=(0,0))`。START失败 runner仍会尝试下一任务，basic_motion由于未完成START会拦运动；这不是 mission 级“启动失败立即停止”。

### 3.3 所有 initial pose 共用的隐含限制

initial配置仅接收 command/axes/target，不接受 timeout 或 speed。每条 `_execute_initial_pose()` 调 `_send_action_goal()` 默认60s。多条 initial 是顺序执行，各自60s，不共享一个任务入口总预算。一条失败就跳过任务体，返回 `{task}.timeout/motion/exception`，然后由runner继续后续任务。移动阶段红黄灯1s交替。

`_send_action_goal` 发目标前 server最多等2s；没有显式 `wait_deadline` 时，accept future与result future没有客户端硬截止，依赖服务端兑现 goal.timeout。mission initial、START、部分球爪offset及投放夹爪动作都存在这个限制；不能把服务端60s/10s写成网络断联时客户端也必定60s/10s返回。

## 4. 撞球任务：完整时序及兜底

### 4.1 目标与入场

当前 order=`[impact_ball_blue]`；蓝球预设 `[4.4,0,0.1]`，红球 `[3.9,0,0.1]`。实际启用颜色的目标位置必须三元素（未启用颜色可以是空列表），启用的颜色必须在共享映射中；检查失败分别 `.configuration`、`.mapping`。相机TF至少一个有效前视目，否则 `.camera_tf`。入场一次 `SET/z→0.2`，30s；后续yaw及保持只选rz/xyrz，不用预设球z修正，BLINE始终dz=0。

### 4.3 视觉兜底并不等于撞击确认

以下归入 ObservationFailure：靠近40s超时；途中首次见球修正后丢失；近场三个方向全无目标；近场或撞击前对准结束无有效目标。

兜底顺序：水平停车→红灯1次→朝当前颜色预设XY（SET/rz，10s）→把预设XY差转body位移→有限BLINE0.15m/s→从正速度开始最多运行15s，动作总50s→取消确认→水平停车→不足15s的剩余时间静止等满。

如果较早到达有限预设终点，不会越过终点继续盲冲，而是在那里等满时间；如果一开始已经在预设XY，跳过BLINE，静止等15s。兜底正常结束返回 `TaskOutcome.ok`，信息明确写“未通过视觉确认撞击”，并立即结束整个撞球任务，不再处理后续颜色。没有接触力、碰撞事件、视觉球摆动或得分反馈的校验。

运动失败（目标拒绝、速度指令失败、服务器不可用、起步超时、取消未终止、BLINE ABORT等）不进入视觉兜底，返回 `.motion`；外部停止/ROS退出返回 `.cancelled`。许多内部超时也被收敛成`.motion`，所以mission的`26rb_hit_balls.timeout`不覆盖全部“撞球阶段超时”。

证据：`26rb_hit_balls.py:211 _run_bline`、`299 _cruise_to_radius`、`339 _near_observation`、`352 _fallback`、`378 _one_ball`、`409 execute`；`hit_ball_config.py`。

## 5. 过门：固定门框、固定射线、条件性放宽高度

### 5.1 当前门数和入场

`gate_count=1`，观测位姿只有 `[1.5,-2,0.2,0]`，单门总预算720s，`max_failures=1`。最多配置1–4门；数组数量必须等于gate_count。`lateral.front=[0,0,0,0]`要求四项，但当前第1项是0，所以横移直接跳过。`max_failures=1`不表示本门重试一次：只有还有下一门且停车确认，才允许跳过当前门；最后一门失败总返回失败。

每门先用实测当前yaw把世界观测点差转换body，`BTRAVEL/xyz`60s；再`SET/xyzrz`完整观测位姿20s。两动作与后续全部阶段共受720s上限。进入下一门重新启动720s，不是所有门共享720s。

### 5.2 搜索与身份选定

1. 到点绿灯；打开接收门框，并记ROS采集时间下限，排除搜索开始前的旧帧。
2. 原地完整观察2s，期间发送零世界水平速度+定深修正；若有新鲜连续三帧确认的轨迹，选择稳定框高度最大的候选，绿2次后进入对准。
3. 没有候选红1次。开启一个共享60s的完整扫描预算：右转+90°，SET回原观测XYZ/yaw（最多20s且受60s裁剪），左转-90°。扫描使用实测yaw累加，速度10°/s，过程中见框也不提前截断。
4. 完整扫完后，从已确认轨迹中选择历史稳定峰值高度最大者，可是当前不新鲜的历史门框。没有候选红2次，`.search`。
5. 有候选绿2次，然后一个10s预算内SET到该门的射线航向并等新帧重获，不能使用扫视时的陈旧像素直接控制。

身份跟踪关键：中心关联门限0.12（按图像宽高归一化的二维距离）、高度比和宽高比≤1.5、成本歧义差<0.15不匹配；每目内部确认3帧。锁定后固定目标ID，不因旁边框更高而更换。跨目接管也要预测bbox、方位差≤20°、消歧及3次连续确认；同刻双目如果三角化不成立，直接否决那个配对，不能借“单目降级”误接另一门。

轨迹代价包含0.4中心差、0.3高度比例、0.2(1-IoU)、0.1宽高比例；状态更新α0.6、速度更新β0.2，速度归一化限±1；高度历史窗3；超过10s且未锁定的某些轨迹可清理。图像边界裁剪的不可见边用预测边保留估计，不把剪裁边当完整尺寸。

### 5.3 对准、横移、前后高度伺服

|阶段|方法|速度/容差|时限|
|---|---|---|---|

### 5.4 高度90秒超时后的特殊分支

仅当异常kind为timeout、当前已到本次前后阶段deadline、尚未到720s总deadline、没有未确认清理、停止速度成功、固定门框仍有效时，允许：停止前后修正→最终yaw严格对准→等新帧→BLINE穿门。这个分支故意不再检查70±1%的高度阈值。

以下情况不能走该降级：超过4m净位移（`.height_unreachable`）、门框丢失超过10s（`.observation_lost`）、720s单门总超时、传输/动作失败、停车或取消未确认。

正常高度达标分支，若闪灯或最终yaw之后新帧高度出容差，返回 `_fore_aft()`，重新得到一个90s预算；循环仍受720s限制。4m判据是相对首次记录起点的沿射线净位移绝对值，不是累计来回路程，来回4m内晃动不会按总路程触发。

### 5.5 丢目、失败、清理与多门跳过

主目帧不新鲜时立即停止水平运动，只保持深度；2s未获主目有效帧释放owner，但保留固定门ID，等待新的有效回调；10s不能重获失败。横移起点、横移进度、前后射线在切目或丢失时不重置。定深 `vz=clip(0.8*(depth-z),±0.12)`；循环0.05s，速度租约max(0.25,3×0.05)=0.25s。

`_park()`在阶段/总超时后另给6s清理预算：禁止再收帧→取消活动action并等终态→零速度（最多2s，另带2s取消确认）→如果清理已确认且未stop，再SET当前实测XYZ/yaw保持。6s是内部主要deadline，不应忽略其调用的取消确认可能再用预算。停车不确认、`.cancelled`、`.odom`立即退出本任务，不跳下一门；其他失败且还存在下一门，未用尽max_failures才跳过。

任务可能返回“过门完成：通过N，跳过M”的成功，意味着已允许跳过的门并不因此把整个过门任务判失败。现在只一门，任何门内最终失败都没有下门可跳。

错误码集合：`.odom`、`.cancelled`、`.timeout`、`.search`、`.observation_lost`、`.height_unreachable`、`.handoff`、`.motion`、`.final_target`、`.exception`。wrapper在相机TF尚未就绪时返回的是旧前缀`26rb_pass_gates.camera_tf`，不是`26rb_gate_task.camera_tf`；依赖精确匹配的失败钩子要留意。

证据：`26rb_gate_task.py:563 _reach_observation`、`588 _search`、`628 _align`、`652 _lateral`、`697 _fore_aft`、`748 _final_yaw`、`792 _pass`、`820 _park`、`857 _run_gate`、`906 execute`；`gate_config.py`、`gate_tracking.py`。

### 6.1 搜索置物框：前视到下视交接

组合任务开始先清本次pickup状态，保留START记录的出发点；默认 `work_depth_m=0.2` 注入共用搜索器作为巡游深度。预设置物框 `[5.8,-0.3,0.5]`；XY用于朝向及兜底，z=0.5不参与搜索移动目标。球环位置没有分别预设XYZ，靠下视检测伺服得到；也不会把目标定位器track来覆盖预设框坐标。

累计计时从BLINE被接受、获取result future之后启动，到动作终态后暂停。它**包含该BLINE的ALIGN、运行、取消终止等待**，并非只算真实forward>0的时间；目标接受等待、停车、前视修正、闪灯不计。与撞球的“靠近40s墙钟”和“撞击8s正速度反馈起算”是三种不同语义。每条搜索BLINE服务端failsafe为remaining+cancel_timeout+1，即首条通常43s；accept最多min(5,move_timeout)=5s；cancel最多2s；不确认终态→搜索失败且本地不继续其他运动。

搜索器失败前通常红3次（每次0.35s、间隔0.25s），设置失败灯已处理；stop或ROS退出不执行这串提示。组合任务使用CollectionFrameSearch原类，其失败码仍是`26rb_grab_golf.search`，不一定是组合任务前缀。

### 6.2 每次尝试之前和之后的共有流程

成功搜索后：SET/z恢复作业深度（10s），用当前实测XY/yaw记第一份frame锚点，depth=0.2。给球、环两个共用PickupController设置相同固定工作深度，然后严格先球后环。

每目标最多3次，包括第一次。尝试计数在机械流程开始前就递增：即使没有看到目标、伺服失败、方向失败、没下潜，也消耗一次，并使下一次目标深度增加5cm。这不是“每成功下潜一次才加深”。球环分别计数，互不累加。

每次 `_mechanical_attempt` 后，无论performed真/假，都进入 `_return_frame`：恢复工作深度SET/z（10s）→回记录frame的XY/yaw SET/xyrz（60s）→强制frame单目像素伺服30s（关闭提前切换球/环）→停车保持10s→更新frame锚点→完整双目复检2s。恢复失败抛异常到外层`.recovery`，整个组合抓取结束，不再执行下一目标；不能笼统写成“球失败永远还能继续抓环”。只有可恢复尝试用尽才继续环。

| P07 |球水平伺服 |30s，归一化像素±0.02、深度±0.03m、保持0.5s |换目/丢失重置保持；无目标零XY继续定深直到deadline |
| P08 |球居中提示 |绿3次 |三次灯共1.55s，不是额外观察成功证明 |
| P09 |按成功相机到圆盘爪TF平移 |BMOVE/xy，[camera_x-claw_x,camera_y-claw_y,0,0]；10s |缺TF/动作失败→本次失败 |

| P11 |下潜到本次机器人目标z |世界Z速度≤0.03，姿态全补偿；第一次0.44，之后0.49/0.54 |最长15s；实测达到立即零速度，停车另给2s |

| P13 |恢复和复检 |按6.2强制frame居中双目复检 |performed=True且verified=True才将球标success |

水平视觉误差经相机安装旋转：`body_image_step = R_optical_to_body*[du,dv,0]*0.6*0.8`，先按body XY合速度限0.03，再转世界坐标取水平；完整世界速度 `[vx,vy,clip(0.8*(0.2-z),±0.08)]` 再乘body→world旋转矩阵的转置成为发送的body速度，因此倾斜时发送body-x/y/z可能同时非零，但设计意图是世界水平移动并保持世界深度。0.6m只是固定控制尺度，不是观测距离。

servo循环0.15s，速度租约max(0.25,4×0.15)=0.6s；每次速度action等待至min(伺服deadline,now+2s)。失去检测时XY=0，继续定深；最终finally发零速度2s，SET完整位置10s。30s不包括最多2+10s停车处理。没有目标时也不是一丢就退出或立刻返回框，先用完当前伺服预算。

### 6.4 下潜深度与机械几何：必须看 base 和爪两套数

默认从0.2到0.44/0.49/0.54，在始终达到0.03m/s的理想情况下分别需8.0、9.667、11.333s。15s默认足够是理想运动推导，若平均速度不足0.016/0.01933/0.02267m/s，三次分别可能到不了目标。失败后零速度、恢复0.2；不按15s盲目冲到底。

本次环/球target z由`基础grab_depth + (attempt-1)*0.05`确定，未设置绝对“池底安全深度”或retry深度上限；增大max_attempts会继续加深。若开始实测z已经比目标更深，remaining≤1e-6会直接认为reached，没有先上浮到该精确目标（正常流程有先恢复0.2来降低这个概率）。

真实URDF圆盘爪位于body `[-0.320,0,0.290]`，发夹爪`[0.080,0,0.130]`。水平艇身时，机器人z=0.44意味着圆盘爪参考点z≈0.73，发夹爪参考点z≈0.57；同样base z，两个爪实际深度相差16cm。第三次则圆盘≈0.83、发夹≈0.67。它们只是爪参考点，不能无条件当接触点/末端尖端。目标frame描述z=0.5也未进入自动下潜计算；是否能碰到球和环必须据机械参考点实测标定。

### 6.5 抓环在球流程上的额外步骤

环检测类别只支持red_ring（映射ID8），gripper_frame=hairpin_claw_link。frame→当前环伺服仍用上述30s、0.03m/s、0.02误差、0.5s保持。环伺服成功后：

1. 清方向样本，从现在开始完整观察3s，采成功下视相机的环二维长轴。
2. servo2松开angle=0，重复3次/0.1s，等1s机械稳定。
3. 再最多5s等待新鲜有效稳定方向；方向quality≥0.8、至少3个样本、轴角散布≤5°，样本年龄≤0.8s。无效方向或quality不达标会清样本；只采成功主目，不用另一目方向凑数。
4. 将像素长轴两点（中心±10像素方向向量）归一化，通过相机TF及艇身姿态转世界射线；与水平面求交差确定无向水平轴。假定环竖直放置、法向水平；这不是完整三维环姿态估计。任一射线z分量<1e-6或轴近零就无效。
5. 在axis与axis+180°中选背离START出发点的方向：方向向量点乘`current_xy-start_xy`为正；恰好垂直/当前位置等于出发点则选转角最小者。不是每次固定朝180°。
6. SET当前XY、工作深度、目标yaw，默认用return_timeout=60s；设置后续环水平伺服的yaw锁定目标（kp1.2、限10°/s、容差3°）。
7. 转向使偏置下视相机移动，所以重新对环水平居中30s；重新记ring_camera_pose。没有重居中就不下潜。
8. 清样本，再最多5s方向复核；最终轴与目标yaw的模180误差≤3°才通过。这里不是持续yaw速度再观察3s，而是SET航向+居中+方向复核的组合。
9. 读hairpin_claw_link TF，用**完整艇身旋转矩阵**把camera.translation-claw.translation转世界，SET新XY、0.2深度、目标yaw（60s）。与球爪BMOVE及投放使用yaw-only偏移不同。
10. 下沉前再SET/z→0.2（10s），稳定1s，下潜到本次ring目标（0.44/0.49/0.54，0.03m/s，15s）。
11. 仅到深度且零速度成功时servo2合爪angle=90，3次/0.1s，等1s；随后恢复工作深度、回frame、强制框居中、双目复检。

方向没稳定、转向后重居中失败或方向复核失败，本次不下潜，但消耗一次尝试；恢复并复检后再试。第三次仍失败则ring_status=failed。中途已经松爪而后方向复核失败的情况下，没有自动重新合爪持物的动作。

### 6.6 双目复检的严苛条件与误判边界

组合任务复检是**回frame中心**后两秒，不是回到球自身先前像素中心再看一眼。需同时满足：

- 两秒完整窗口内任一眼的任一回调看到当前目标，就锁存seen_target=True，本次不能确认抓走；后来消失也不翻回成功。
- 两个眼分别收到窗口内新回调；最后消息≤0.8s，且连续“无此目标”回调时间跨度≥0.8s；有>0.8s消息间断则重新算。
- 窗口结束时至少一个眼当前新鲜消息里还能看见collection_frame_down；不是摄像头全黑/完全偏离框就当抓走。
- 事件队列必须无漏段；缓存deque最大256，消费时序号跳号视为lost_events，不能确认抓走。
- 任务未停止。最终只有 `performed and verified` 才success，单凭目标不见不会把没下潜的失败动作认成成功。

该判据证明的是“居中框视野里目标持续不见且机械流程完成”，不是“目标在爪内”。球被推走、掉出框、误检/漏检、目标被艇体遮挡都仍可能满足消失；没有夹爪力/限位/持物图像传感器确认。主runner没有采集时间老化校验和capture去重，因此新回调重放旧图像的情况仍需另查。

### 7.3 所有失败与部分成功情况

- TF未就绪→`.camera_tf`；共享mapping无target_rack_down→`.mapping`；前视类缺失会在搜索器返回`.search`。
- 视觉伺服期间目标丢失只是停止XY、保持锁定深度并继续等；30s无达标最终`.timeout`，不会放球。
- 速度action失败、几何计算失败、停车失败→`.visual_servo`或`.motion`/`.timeout`，取决于`_last_motion_failure_kind`及fallback helper；finally停车动作可能改变这个字段，不能只依据失败名称猜超时码。
- 圆盘爪TF/定位失败→不释放球，也不处理环。
- 已释放球之后发夹爪定位失败→不释放环；代码不回收刚放球，也不重试整个投放。
- 三次释放期间stop可能已经发了1–2条命令，不能推断零释放；没有单项“球已放/环未放”的持久化状态，仅靠日志还原。
- 完成绿灯被stop也返回`.stopped`，此时物品指令可能已经全发送。
- 未捕获异常由runner规范化为`.exception`。投放execute的finally只是灭灯，不是一个通用恢复运动或舵机回退流程。
- 无论抓取状态如何，此任务都会依次发球和环释放；无落入rack视觉确认、目标位姿入筐判据、计分裁判反馈或舵机机械闭环。不能把 `TaskOutcome.ok()`写成“两个物体已成功进入rack”。

证据：`26rb_drop_ball_target_rack.py:106 _observe_rack`、`184 _servo_rack`、`281 _align_disc_claw`、`302 _align_claw`、`360 _release_ball`、`376 _release_ring`、`391 execute`；`collection_frame_search.py:506 TargetRackSearch`。

## 8. 回家：水平返航与开环上浮分开

水平返航完全放在mission initial.poses中：WTRAVEL到[3,-1,0.2]→WTRAVEL/xy到[0,0]→SET/rz到0°；每条默认60s。返航任务体`return_origin`本身不会规划回原点、不会执行XY回家；单独运行return_origin.yaml只上浮，不自动回XY原点。

上浮先取起始z，参数target=-0.3、speed=|0.05|、timeout=max(0.1,30)、period=max(0.02,0.05)。distance=start_z-target：≤0直接成功；>0时duration=distance/speed。若duration>30，立即返回失败，不先上浮30s再报超时。若start_z=0.2，duration=(0.2+0.3)/0.05=10s。

之后按body vertical_mps=-0.05循环续发，每0.05s，租约0.25s；deadline按估计duration墙钟设置。finally发零速度。速度失败、零速度失败或stop都失败。成功仅把_cmd_z估计设置为-0.3，并记录“估算目标”，不按实际z闭环终止，不检查是否出水、航向是否达0°、是否在原点范围内；姿态倾斜时body-z上浮可能产生世界XY分量，与组合抓取下潜世界Z完整补偿不同。

没有自动DISARM、关闭ARM心跳、锁定安全停止、待人工回收状态或电池耗尽返航联动。basic_motion START建立的ARM心跳会继续存在，直到新的START、安全生命周期事件或节点退出等另行停止；任务列表完成并不等于MCU上锁。

此处30s不是可靠客户端全程硬上限：每次速度action未传wait_deadline，客户端等待future有可能卡住；没有实际z复验。返航途中initial失败时不执行上浮任务体，直接记录失败并结束列表。因此“回家失败自动原地上浮”的兜底也不存在。

证据：`task_runner.py:1232 _task_return_origin`、`737 run_task_list`；`uv_control/basic_motion.py:595 _heartbeat_cb`。

因此在水平艇身yaw=0条件下：下视到圆盘爪所需艇体平移为 `[+0.190,±0.0305863366]`；下视到发夹爪是 `[-0.210,±0.0305863366]`。符号按成功目左负右正。球与环释放目标两爪x相差0.400m，必须从同一相机锚点各自算；不能再次叠加下视到爪偏移。旧高尔夫yaml的注释写 `+0.300m`，已经不符合真实URDF，应以运行时TF为准。

### 9.4 仿真scene坐标不能直接等同START后的odom

## 10. 控制器、固件和停止保障：任务之外的关键边界

### 10.1 START 后真正使用的原点公式

MCU `Common/MotionContext.cpp:updateOdomLocked/trySetOrigin` 已确认实现，而非仅依赖注释：

```text
origin = 当前有效 raw-nav 的 [X0,Y0,Z0,0,0,yaw0]
odom_x = cos(yaw0)*(X-X0) + sin(yaw0)*(Y-Y0)
odom_y = -sin(yaw0)*(X-X0) + cos(yaw0)*(Y-Y0)
odom_z = Z-Z0
odom_yaw = wrap(raw_yaw-yaw0)
roll/pitch 和机体 twist 不因原点重置而归零
```

SetOrigin 要求未 ARM、导航有效、深度源有效、raw-nav 样本年龄 ≤200ms。成功递增 `origin_generation`（跳过0）、把 setpoint 清零并重新要求 ARM 心跳资格；单纯 DISARM 不清除此 boot 的原点。因而 `work_depth_m=0.2` 是比 START 时 raw-z 深0.2m；如果 START 在水下0.12m执行，工作绝对深度推导为0.32m，不是0.20m。机器人下潜目标0.44/0.49/0.54与返航目标-0.3同样相对该原点。以START时水面偏差变化造成的所有深度偏移，不能靠改物体坐标的z解决。

定位节点将 MCU odom 作为来源，默认30Hz发布；`position_timeout=2.0`、SetOrigin服务阶段3.0、等待匹配generation的reset-frame阶段1.0，各阶段预算分开。它同时检查odom消息接收是否新鲜和nav_timestamp是否推进，避免只重复发布旧导航就被当成新导航。BasicMotion还有自己1.0s的状态门槛，通常更严。任务层 `_latest_robot_pose()` 本身没有同等新鲜度判断，见第2章。

### 10.2 各层停止机制不能互相替代

| 机制 | 默认时限/周期 | 实际行为 | 不保证的事情 |
|---|---|---|---|
| BODY_VELOCITY租约 | 多数0.25s；抓取水平0.60s；投放水平0.80s | BasicMotion进程仍活着且timer可运行时，超期发零机体速度 | 进程崩溃后不能靠已消失的timer发零；不是MCU速度指令TTL |
| BasicMotion动作取消 | cancel回调先发零；BLINE另有终态/保持处理 | 接受取消请求；动作循环随后响应 | cancel请求被接收不等于action已经终态；任务必须等result |
| BasicMotion safe-stop | 显式服务，锁存 | 发零机体速度，拒绝后续goal；显式clear服务解锁 | 不等同DISARM；ARM心跳仍可继续；零速度也会在goal回调被锁存拒绝，内部“zero always accepted”注释只覆盖execute分支 |
| MCU ARM心跳 | 默认15Hz；已ARM间隔>1000ms判失联；Monitor10Hz | 强制DISARM、控制层NONE；未ARM要求≥10次且持续≥1000ms | 只要心跳仍在，不能靠此机制判定任务卡死、目标丢失或电池低 |
| MCU软/硬看门狗 | 软阈值3000ms，默认只检查micro-ROS | SoftWatchdog失败后Monitor停止喂硬件IWDG，最终硬复位 | 不是精确3s后推进器停；硬IWDG还取决于LSI/Reload/Prescaler和下游板失联策略 |
| hw_manager监控 | 默认7s，summary1Hz | 心跳丢失设DEGRADED并报错；电池<14V告警 | 代码此处没有自动返航、上浮或DISARM |

固件 IWDG 源码配置 Prescaler=4、Reload=2999、Window=4095；准确时间应以板上LSI频率为依据，不能把寄存器数值直接称为3000ms。MicroRosSubscriber没有为每个速度setpoint实现独立的超时租约；任务层/BasicMotion租约不能宣传为“MCU自主TTL”。

MCU的导航有效窗口常量是10000ms；真实INS需状态3或4并有新样本，z源默认M14，z有效性还受源新鲜度约束。`system.soft_watchdog.timeout_ms=3000` 同时参与深度源/接收监控，不只是看门狗喂狗。`force_nav_valid=true` 只绕过ROS BasicMotion readiness中nav_valid布尔值，并不会改变MCU `onSetpoint()` 对无效导航的拒绝。

证据：`third_party/AUV_zit6_cmake/UserApp/Component/MicroRos/MicroRosSubscriber.cpp:202 onSetpoint`、`Application/ControlTask.cpp:460 computeAndPublish`、`Component/Chassis/ChassisManager.cpp:19 update`、`Component/Chassis/CascadeController.cpp:153 update`、`Component/Safety/SafetyMonitor.cpp:19 check`。

**特别重要的跨层缺口：** MCU `onSetpoint()` 对 POSITION/VELOCITY 都检查导航有效；导航失效时连零BODY_VELOCITY也可能被拒绝。`ControlTask::computeAndPublish()` 每10ms仍更新控制器并在armed时发其力输出，未找到此处按nav_valid强制置零的分支。SafetyMonitor在已ARM分支只看心跳，不会因为导航无效立即DISARM。因此“ROS已发零”不能等同“MCU已应用零”；尤其心跳仍正常、导航失效、旧速度目标存在的组合，需要真实链路验证或实现更强停止路径。此结论来自源码联读，离线任务测试不能证明实艇已安全停止。

### 10.3 普通位置动作的速度由什么决定

固件默认 `planner_enabled=false`。此时位置外环直接对当前误差算速度目标，既不执行KinematicProfile位置/速度规划，也不加其速度、加速度前馈。因此下面两列不能混称为同一个速度上限。

| 轴 | 位置PID输出限幅（planner关闭时的外环速度量） | profile.max_v / max_a（开启planner时才参与规划） | 速度PID输出限幅 |
|---|---:|---:|---:|
| X | 0.50m/s | 0.80m/s / 0.40m/s² | 0.80 |
| Y | 0.20m/s | 0.60m/s / 0.30m/s² | 0.90 |
| Z | 0.50m/s | 0.50m/s / 0.30m/s² | 0.80 |
| roll | 0.50rad/s；位置Kp=0 | 0.50rad/s / 1.00rad/s² | 0.00 |
| pitch | 0.50rad/s | 0.50rad/s / 1.00rad/s² | 0.80 |
| yaw | 1.50rad/s≈85.94°/s | 1.00rad/s / 0.80rad/s² | 1.00 |

这不是实测艇速：外环的world速度还会按完整姿态转为body，内环作用于速度误差，最终力输出限幅[-1,1]；推进器、阻力、负载、电压和误差都影响实测速度。WTRAVEL的0.6/0.4步长也不是0.6/0.4m/s。BODY_VELOCITY在planner关闭时直接把目标机体速度交给内环，**不会额外用profile.max_v作通用限幅**；当前各任务本身的限速与BLINE的限速因此很关键。

### 10.4 真机启动入口决定参数覆盖和自动启动

`real.launch.py profile:=task` 准备硬件、定位、BasicMotion、相机、AI和录制，但不会启动task_runner、不会替你发送START。应把“系统组件启动成功”和“mission开始”分开记录。`check_backend_health=false`、`enable_perception_gate=false` 默认只显示/跳过相应健康观察，不能据此认为目标检测、导航和原点已就绪。

单独 `uv_task/task_launch.py` 默认 `auto_start=true`，mission默认robocup_26.yaml；`params_file`默认空。`real_test_runner.yaml` 内容虽然是 `debug_mode=true`，但只有显式加载才生效，不是所有真机任务默认都在debug模式。不要被runner内残留的“supervisor auto_start disabled”注释误导，实际启动参数以当前launch构造为准。

检测器普通节点/感知launch默认 confidence=0.5；**当前real_startup启动感知时明确覆盖为0.8**。搜索任务再设0.02并不能恢复上游已丢掉的0.02–0.8框。前后模型路径可分别覆盖；映射发布器与实际模型必须一致。real_startup在adopt/auto时可能复用已有节点，报告中的启动命令默认也不等同已复用节点的实际参数。

### 10.5 舵机与灯光链路的边界

灯光原始值OFF=0、RED=1、GREEN=2、YELLOW=3、BLUE=4。通用任务失败且专用任务没有声明自己处理灯光时，runner只设置红色阶段灯；不是所有失败都自动“红闪三次”。initial结束在未stop时恢复黄，initial失败随后设红；专用搜索/过门的红灯次数另按各自阶段处理。`_set_task_phase_light`同色不重复发，具体闪灯使用强制set/off并等待。

舵机发送链：`task_runner.set_servo`原样填float angle → hw_manager原样转发 → MCU `onServoCmd`只校验ID为1/2且angle有限 → driver原样填ServoPacket；servo1包类型0x02，servo2为0x04。任务写0/90“度”，一些函数形参和MCU日志却标rad；这条链没有deg↔rad转换，最终VIT6板解释什么单位须按其协议/实际固件核实，不能把日志标rad当作已换算。

`onServoCmd`没有ARM或nav_valid门禁，也没有[-180,180]范围限制；任务构造器的角值校验不等于MCU对其他发布者也有同样限制。mission stop不自动让两爪复位，也不能撤回已发送的舵机包。

MCU `getServoAngles`返回的是最近一次`transmitDMA`成功后的目标缓存，随后被ServoState发布并由hw_manager转发；它不是读到舵机电位计/编码器的实际角度。DMA成功仅表示UART传输已启动，仍不证明板接收、机械到位或物品释放。底层UART忙时最多6轮×1ms等待，再判断是否能启动DMA；失败写MCU日志，任务层publish并不接收这条失败为动作结果。三次0.1s重发提高机会，不能产生机械闭环。

证据：`task_runner.py:454 set_servo`、`822 _execute_task`；`uv_hm/uv_hm/hw_manager.py:367 _servo_command_cb`；`third_party/AUV_zit6_cmake/UserApp/Component/MicroRos/MicroRosSubscriber.cpp:309 onServoCmd`、`Component/MicroRos/MicroRosPublisher.cpp:282`、`Peripherals/MotionController/src/MotionController_Driver.cpp:74 setServoAngle`、`Porting/MotionController/src/MotionController_Porting.cpp:18 transmitDMA`。

## 11. 独立 `26rb_grab_golf` 与组合抓取的区别

此独立任务当前未作为mission条目启用，但组合任务复用了其水平伺服/外参对齐控制器，不能把两个任务的完整垂直和复检策略混用。

| 项目 | 独立grab_golf | 组合grab_ball_ring |
|---|---|---|
| 目标 | 一个pink/yellow高尔夫球 | 一个球→一个red_ring |
| 水平伺服深度 | 第一次伺服时实测z锁定 | 强制配置work_depth=0.2 |
| 下沉 | BODY vz=0.03，固定8s；参数旧注释5s不准 | 按实测z到0.44/0.49/0.54，最多15s |
| 上浮 | BODY vz=-0.10，固定5s | SET/z回0.2，单次10s |
| 姿态补偿 | 旧垂直body轴，姿态倾斜会引入world XY | 组合下潜使用world垂直目标变换 |
| 理想净深度变化 | +0.03×8−0.10×5=-0.26m，之后定位回记录姿态 | 每次机械阶段后恢复配置作业深度 |
| 重试 | max_grab_retries=2，首抓后最多2次 | 各自max_attempts=3，含第一次；每次失败都消耗 |
| 重试触发 | 主要是机械动作成功但复检失败；部分机械失败立即退出 | 单次各种失败可以进入下一次，恢复frame失败则终止 |
| 复检相机 | 本次成功伺服的单目 | 两目都要有连续新回调，且末尾至少一目见frame |
| 复检看到目标 | 窗口前段看到、后段连续消失≥0.8s仍可能成功 | 完整2s内任何一次看到都否决 |
| 全任务时限 | 没有独立全局deadline | 同样没有独立全局deadline |

独立构造器fallback还与YAML不同：缺参数时下降默认0.1m/s×5s，水平projection默认/限速也可能与YAML0.6m、0.03m/s不同。直接调用类必须传经config_loader展开后的参数；把嵌套YAML原样传给构造器会让大量`.get('flat_key', default)`悄悄走fallback。

## 12. 失败处理总矩阵：触发、现有动作、后续去向

以下“下一任务”均受runner的全局 `stopped` 约束；局部return false没有自动设置该锁存。表中“禁止后续动作”只在该任务类内部有效，除非同时停止了runner。

| 触发/现象 | 当前任务内处理 | 会继续什么 | 缺口/排查关键 |
|---|---|---|---|
| YAML重复键、未知键、类型/finite校验失败 | config_loader拒绝加载 | 不进入该配置流程 | 先看完整报错和被选中的task文件；不要把它当视觉超时 |
| mission未启用撞球/过门 | 没有对应动作 | 直接抓→放→回 | 空日志不是任务失败，根本未执行 |
| mapping10s未收到 | main退出 | 任务节点结束 | 先看mapping发布、模型名称；等待更久动作超时无效 |
| 个别canonical class缺失 | 对应任务mapping失败；组合目标可标failed | runner下一条；组合另一个目标可能继续 | 不是把class_id手改成测试stub值 |
| TF任一眼缺失 | runner全四眼snapshot不可用，任务camera_tf失败 | runner下一条 | 单眼够用的算法也受全快照门槛约束 |
| START无法解除ARM/SetOrigin/匹配generation | START失败并关闭相应心跳/状态 | runner仍可能尝试后续 | 后续动作会被未START/未ARM阻止；没有自动重来START |
| initial pose超时/动作失败 | 该任务体不执行，返回initial阶段失败 | runner下一任务 | 返航initial失败也不会自动执行原地上浮 |
| 普通goal发送后action响应/结果丢失，无wait_deadline | 客户端等待可无上界 | 无法进入本任务恢复逻辑 | 服务器timeout不等于客户端通信deadline |
| BLINE取消请求后result不终态 | 各专用任务拒绝继续交接/发SET | 此任务失败后runner仍可能下一个 | 需全局停止/安全态与结果终态一起确认 |

### 14.4 debug执行不会自动合并任务YAML

`/auv/mission/execute` 只在debug_mode=true生效，JSON params直接传到任务handler，不调用load_task去补YAML默认；接口返回success表示“已接受并启动后台线程”，不是任务已完成。空JSON或只给一个参数时，许多值取构造器代码fallback：例如撞球蓝球预设可变为[2,0,0.2]，抓取水平scale可变0.8、限速0.08，而当前YAML是0.6、0.03。

`request.timeout>0` 存入 `_debug_timeout`，覆盖每次runner action的server timeout；专用任务自己维护的搜索钟、30s伺服窗口、15s下潜或720s单门窗口不被它统一覆盖，专用wait_deadline仍裁剪action。故“debug timeout=300”不是让整个任务最多300s，也不是把所有子阶段都变300s。BLINE有的专用调用直接用action_client，更不经过该runner覆盖。

debug结束日志会打印成功/失败，但除basic_motion_test的专用状态分支外，当前TaskStatus空闲时显示调试等待文字，不能只看服务响应或最后一个STATUS来断言任务完成。应保存完整日志、failure_code和动作result。

TaskState虽然有bias坐标转换方法，runner注明仍是opt-in；本链条的 `_latest_robot_pose`、新任务预设位置、抓取锚点直接用raw odom，没有自动使用bias去纠正漂移。修改state.bias不会自动移动当前目标、修正所有预设点或处理已飞行goal。

### 14.5 stop、重新run与节点退出的实际区别

`/auv/mission/run start=false`只设置stopped=True并立即回复“已停止”，由任务/action等待循环随后响应；`/auv/mission/stop`调用 `_stop_active_motion`，设置stop、取出当前goal请求异步cancel，也立即回复，不等cancel acknowledgement或result，更没有实测停止确认。它没有在runner里直接写MCU零推力，日志明确把速度租约/中性保护交给BasicMotion。两个服务的成功响应都不能作为“实艇已停稳”的证据。

再次run必须等running/debug_executing清除，否则拒绝并发。新run重载mission，`run_task_list`把current_index=0、历史failure字段清空，重新从第一项开始；PAUSED不是有持久检查点的继续执行。如果第一项仍START，会再次建立原点并清抓取状态，不自动保留此前持物/部分投放结果。

只退出task_runner会请求取消它记录的活动goal，BasicMotion若继续运行仍可能持续ARM心跳，最终依赖其动作清理/速度租约。BasicMotion自身退出时则尝试一次零速度、关闭ARM心跳、结束START waiter并取消timer；此后MCU心跳超时会触发上锁，但准确停机时刻仍受进程退出、DDS送达和MCU监控周期影响。这与safe-stop锁存但心跳继续、任务列表DONE但心跳继续是不同路径。

`_last_failure_code`保存的是最近一个失败，不是完整持久事件账本；它保持非空使本次mission最终ERROR。后续成功不清掉它，而下一次run会清掉；完整失败序列应从日志/记录恢复。

证据：`task_runner.py:400 _stop_active_motion`、`2034 _run_task_cb`、`2072 _stop_task_cb`、`737 run_task_list`；`basic_motion.py:306 _on_context_shutdown`。

## 15. 上游方向检测、运行时裁剪和定量推导

### 15.1 环方向有效的必要条件

检测器默认 `ring_orientation_enabled=true`、ROI scale1.2、最少24个红像素、quality≥0.8。仅down相机且映射类red_ring才计算方向。HSV红色两段H=[0,18]或[165,180]、S≥45、V≥30；3×3闭运算一次，8邻域连通域，按原bbox内红像素数量选域、中心距离打破平局。不是简单取整个ROI中最大红物体。

bbox碰真实单眼边界（x1/y1≤0或x2≥width−1/y2≥height−1）无效；输入不是uint8三通道、bbox无面积、参数非法、连通域太少、PCA退化、5–95%投影轴长度<12px也无效。quality=`(λlarge−λsmall)/(λlarge+λsmall)`；0.8阈值推导要求主/次特征值比至少9（次值>0时），对应标准差轴比至少3。正视近圆环、背景红色干扰、色偏/遮挡会造成方向无效，即使YOLO已经能报red_ring框。

方向是无向轴[0,180)，以float32舍入后再次mod180。任务另需3个样本、样本接收年龄≤0.8s、模180分布≤5°、转向后再验yaw误差≤3°；因此“detector orientation_valid=true”仍不足以立刻下潜。

检测器直接运行时的代码默认权重/共享映射是 **HQQ7_aug.pt / HQQ7_aug.yaml**；审查末次复核时，`real.launch.py` 和 `perception_launch.py` 已改为前视默认 **HQQ6_aug.pt**、下视默认 **HQQ7_aug.pt**，以绝对路径传入。两套YAML的canonical类别ID相同；这是启动覆盖，不是共享映射跟随前相机自动变成HQQ6。仍可被 `UV_YOLO_MODEL`、front/down_model_path和 `UV_MODEL_MAPPING_FILE` 等覆盖。robotcup20260901.yaml保留同一套0–11 canonical类别，是任务配置注释引用的旧文件名，不能写成当前一定在跑robotcup20260901.pt。权重label集合会与共享映射逐ID核对，不一致时对应相机model_valid=false，检测线程等待/丢帧；front/down双模型必须都兼容同一共享mapping。

### 15.3 深度和图像容差的计算示例

组合从work_depth0.2以0.03m/s下潜，理想三次时间为8.000、9.667、11.333s；若要在15s内达0.44/0.49/0.54，平均world-Z速度至少0.0160/0.01933/0.02267m/s。第三次可容忍的平均速度损失更小；重试更深不保证更容易成功。

真实下视fx约1159：normalized误差0.02对应主点附近约23.2px，投放0.035约40.6px；仿真fx672.18对应13.4px和23.5px。真实左主点[679.12,510.67]、右主点[694.99,549.47]，都不是简单[640,480]；算法按标定中心去畸变，肉眼看图像几何中心不一定等于伺服零点。偏离主点后畸变使像素对应关系不再严格线性。

### 15.4 BLINE离线运动学敏感性演示

|---:|---:|---:|---:|
| 0 | 7.20s | 14.50s | 0.9788m |

### 15.5 夹爪触达深度必须按机器人原点和末端一起核算

机器人目标Z不能单独拿来与球/环中心比较。水平艇身且使用真实URDF时：

```text
world_disc_reference_z = origin_raw_z + odom_robot_z + 0.290
world_hairpin_reference_z = origin_raw_z + odom_robot_z + 0.130
```

同一个机器人抓深0.44，对应两个夹爪参考点差0.160m；所以“球和环都用0.44”不代表末端在同一深度。若只是演示性地把固定scene的起始world-z=0.12与真实URDF组合，三次抓深0.44/0.49/0.54给出disc参考z=0.85/0.90/0.95、hairpin参考z=0.69/0.74/0.79。这些不能直接当Stonefish碰撞端点：URDF固定frame不一定等于接触端，仿真模型/实物爪尺寸、姿态和摆放仍须核对；本表也没有假定该混合配置就是当前运行场景。

完整姿态下应使用 `p_world_tool=p_world_base+R_body_world*p_body_tool`，roll/pitch会改变工具的world-Z及XY。当前球的相机到爪平移和投放偏移只按yaw处理，环对齐使用完整姿态的world XY；二者的倾斜误差处理不同。固定投影尺度0.6/0.8也不是实时测得相机到物体距离，深度变化时控制增益与实际接触位置必须分别评估。

## 17. 对每类失败应该怎样处理：现状与改进契约

第12章是已实现分支；下表是基于已发现缺口建议形成的明确契约，**尚未写入任务代码或参数**。这里不另造一套“当前已经有”的自动恢复流程。

| 失败类别 | 当前行为要点 | 建议的处理契约与验收条件 |
|---|---|---|
| START原点/ARM失败 | 本任务失败；runner可能继续 | 后续所有运动禁止推进；记录origin generation、ARM mode、readiness失败项；重新START须在已DISARM且新导航有效时执行 |
| goal未接受/服务断连 | 各动作不同；部分客户端无deadline | 每次accept/result/neutral/cancel都受同一阶段绝对deadline约束；不把server timeout当client timeout |
| 取消已接收但旧goal未终态 | 局部任务可能失败返回，runner可继续 | 全局进入停车未确认状态，禁止新goal；至少取得终态和新鲜实测停止证据，不能靠等待固定2s就推定停稳 |
| odom陈旧/导航失效 | ROS与MCU门槛不同；零速度可被MCU拒绝 | 进入独立停止链路；检查MCU实际控制层/ARM/目标与力输出，不能只检查ROS publish返回；无导航情况下的停车/上锁需专门实机验证 |
| 相机断流/重复capture/旧header | front严格、共享down偏接收时间 | 将capture/header去重和年龄校验统一到下视入口；断流与“新鲜空帧”分开；断流不得证明物品消失 |
| 类别映射缺失/模型不兼容 | 多数任务mapping失败或对应detector禁用 | 在开始移动前验证两相机model_valid、mapping版本、类别ID；修配置后重新进入明确阶段，不靠盲搜补偿模型错误 |
| 看不到撞球 | 当前可盲行15s后OK | 竞赛容许盲行则结果标为“未确认撞中/降级完成”，与撞中成功分开；禁止把fallback OK累计为物理得分 |
| 门框暂失 | 零XY→保持身份重捕获10s；超时可能跳下一门 | 保留目标identity、路径ray、当前travel量；恢复前要求新帧确认同一门；最后一门失败与允许跳门结果明确上报 |
| 门前后调整未达70% | 限定90s退化可strict yaw后通过 | 将退化结果单列，记录实际height/cross/depth/yaw；不要把4m上限、目标丢失、整体720s超时也纳入同一退化 |
| 某次球/环机械失败 | 本次尝试消耗；回frame成功后复检/再试 | 区分未开始下潜与确实触达失败；更深重试前核对末端深度、剩余水深与对象位置，不能让纯观测失败无条件加深 |
| 回frame失败/清理未确认 | 当前组合整体recovery失败 | 不继续下一种物品；全局不应接着无条件投放；保留每件物品status及实际是否仍持有的未知状态 |
| 球/环复检消失 | 当前用双目新鲜空帧判定 | 保留“视觉移除成功”证据，同时把是否夹持标为独立状态；遮挡、推出视野、掉落应能区分或保留unknown |
| 只抓到球或只抓到环 | 当前投放仍两套释放 | 投放按每件持有状态选择释放；`unknown`需单独策略，不能等同空手或已持有；用例覆盖两种部分成功 |
| 球已释放但环定位失败 | 返回失败，无部分释放账本 | 记录球释放已发/物理确认、环仍持有/未知；重试不能重复假定球仍在爪上，航点切换需考虑环负载 |
| 舵机无动作/堵转/释放不掉 | 只有消息重发和等待，无反馈 | 把发送、驱动接收、机械到位、物品落入rack区分；若暂无反馈硬件，报告只能给“已发指令”结论 |

### 17.1 建议处理优先级

1. **先解决全局运动互锁**：START失败、旧goal取消未确认、导航失效及停车未确认，不能继续产生下一任务运动。确认停止必须跨到MCU实际状态。
2. **统一几何和部署来源**：disc_claw−0.320/−0.380选定真实标定值后同时更新源、测试、安装TF；记录resolved mission、模型路径、共享mapping、实际参数与原点。
3. **再使完整比赛流程可执行**：明确启用撞球/门并排序，确认撞哪几个球、过几门、每个门的观测位姿；不是简单取消注释。
4. **补结果账本与验证**：物品每件持有/未知/释放状态，撞球物理结果、门通过判据、投放落点、返航到达与最终ARM状态，各自可审计。
5. **最后调水中速度与时间**：以实际转向、下潜、姿态误差、相机时延和负载数据调整30s/15s等预算；保持任务级、动作级、清理级预算的分层关系。

### 17.2 用户指定流程的配置审阅目标

以下仅是应审阅的顺序，未替换当前mission：

```text
START（成功且新原点确认）
 → 撞球入口位姿 → 26rb_hit_balls（核对blue/red order与fallback结果语义）
 → 过门入口/观测点 → 26rb_gate_task（核对gate_count与poses等长）

```

任何一段新增运动都应核对其坐标是本次START后的odom，axes实际使哪些字段生效，上一段结束后yaw/z是否满足下一段假设。现在的入口坐标与固定scene摆放不能不经转换直接拼接使用。

## 19. 参数修改时的校验边界与容易误配的字段

| 配置入口/任务 | 明确校验 | 易漏的边界 |
|---|---|---|
| YAML加载器 | 重复键报错；未知参数报错；严格类型；数值有限；bool不当数值；float字段允许整数写法 | mission覆盖先做部分校验，合并后再做完整语义校验；debug直接params不经过这一整条加载链 |
| initial_pose | 仅command/axes/target；command白名单；axes只x/y/z/rz且不重复；target恰好4个有限数 | 不能把timeout/speed塞进initial；axes未选字段即使写了数也不驱动该轴 |
| 撞球 | order非空、只blue/red canonical名、不重复；目标位置空或3位；BLINE速度严格(0,0.18) | 实际启用颜色还需有3位位置；未启用颜色允许空；debug未知字段不一定像YAML那样拒绝 |
| 撞球时限 | charge/fallback总timeout必须严格大于duration；yaw保持时间≤两个yaw阶段时长 | 满足这条只表示留出了一点时间，不保证足够30s起步+取消清理 |
| 门 | 1–4门，poses数量与gate_count一致，每项4位、z≥0；depth/lateral.front都四位 | depth.front虽已不驱动当前定深，但显式给出时仍可能与poses.z触发冲突；过期字段不是任意值都被忽略 |
| 门范围 | scan角(0,180]；confidence(0,1]；height target(0,100]且容差小于target；最终yaw最小时长≤最大时长 | 所有门仍各自720s，不是配4门后每门180s；lateral数组可带符号，不等同绝对world-y |
| 门旧面积字段 | target_area及area_tolerance仍有范围校验 | 已不用于前后成功判据；改80%面积不会把当前70%高度目标改掉 |
| 组合抓取 | work/grab/retry_step有限非负；grab≥work；max_attempts整数≥1；环class仅red_ring；角值[-180,180] | max_attempts没有固定3的上限；retry_step不受池底几何自动约束；旧max_grab_retries明确拒绝 |
| 组合方向 | min_samples整数≥1，quality[0,1]；时间/gain等正数 | 能通过参数校验不表示物体在图像上有足够主轴质量；quality阈值还受上游检测器制约 |
| 投放 | 环释放角度、重发与间隔等专门校验，舵机ID固定为球1/环2；servo多项clamp | YAML rack.z=-1合法但不用于当前机器人深度；换该z不会改变投放高度 |
