## 2. 第一次运行就抓到的错误：两行消息类型写错了

场景里 `<ros_publisher topic=.../>` 声明的发布者，其消息类型是 **C++ 填的**
（`ROS2Interface.cpp` / `ROS2ScenarioParser.cpp`），而 checker 对这类行只能校验
"场景声明了这个话题"——**类型列一直是自由声明**。快照实测差了两行：

| 话题 | 文档（错） | 实测/证据 |
|---|---|---|
| `/auv/dvl_altitude` | `std_msgs/Float32` | **`sensor_msgs/Range`**（`PublishDVLAltitude` → `Publisher<sensor_msgs::msg::Range>`；`radiation_type=ULTRASOUND`、`field_of_view=2·beam_angle`） |
| `/auv/thrusters_state` | `std_msgs/Float64MultiArray` | **`stonefish_ros2/ThrusterState`**（`ROS2ScenarioParser.cpp:442` `create_publisher<stonefish_ros2::msg::ThrusterState>`），实测 **99.8 Hz**（跟物理步长） |

只改文档不够（下次还会漂），所以加了 `test_scene_publisher_types.py`：把
「话题 → 契约类型 → C++ 类型 → 证据锚点（函数名或 `file:line`）」逐条钉住，
**证据本身**也要断言（函数体里确实 publish 了那个类型），并且有一例把这两条错误值
**重新注入**，证明守卫会报出来。这类"源码里看不见的事实"从此有可执行证据。

## 3. 新登记 B20：`/basic_motion/pose_info` 只有设计值的一半（未修）

测频率时发现 `pose_info` 与文档的 30 Hz 不符，于是做了三组对照：

| 场景 | `ros2 topic hz` | 独立 depth-1 计数（10 s） | 说明 |
|---|---|---|---|
| 完整 SIL console 栈 | 10.3~19.9（抖动） | **15.58 Hz** | 发布侧确实 ≈15.6 |
| **只跑 `basic_motion`** | — | **29.93 Hz** | 代码路径本身没问题 |
| 同窗口对照 `/zit6/state/pos` | 29.949 | **29.77 Hz** | 测量方法与机器都能跑 30 Hz |

所以这不是测量误差，而是**完整栈里 `basic_motion` 的 30 Hz 定时器丢了一半节拍**。
怀疑方向：它用 `MultiThreadedExecutor`，而 30 Hz 的 `_pose_cb`（订阅 `/zit6/state/pos`）
与 30 Hz 的 `_publish_pose_info` 定时器**共用默认互斥回调组**，互相串行 + 负载下 GIL 抖动，
而 rclpy 定时器**不排队**。影响：`position`/`navigator`/`task_runner` 都把它当 30 Hz 位姿源。
**只登记未修**（本轮是文档轮），修复方向与"必须在完整栈里复测"写进了 `roadmap.md` B20。

> 测量方法上踩过一个自己的坑（记录以免重犯）：一次探针脚本里把
> `export … && source … && timeout ros2 run … &` **整链**后台化了，于是父 shell 从未 source，
> 探针 import 到了**另一个 checkout（AUV2026）的 `uv_msgs`** 而报 `ImportError: PoseInfo`。
> 教训：`&` 要只作用于最终那条命令，且先 `python3 -c "import X; print(X.__file__)"` 确认解析路径。

## 4. `axes` 字段其实会生效（文档错了）

审计 `basic_motion` 时发现 `axes` 不是"仅用于日志"：

```python
if req.cmd_type == BasicMotion.Goal.SET:
    axes = req.axes or 'xyzrz'
    if 'x' in axes: tx = x          # 只更新列出的轴
    ...                             # 其余轴沿用上一目标
```

- **SET / WMOVE / WTRAVEL**：只有列在 `axes` 的轴更新为目标值，其余轴**沿用上一目标**；空=全轴。
- **BMOVE / BTRAVEL / START**：完全不参与。
- 极性与 `ZitSetpoint.type_mask` **相反**（那里 1=忽略该轴）——两个"轴掩码"含义相反，值得单独记一笔。

已更正 `CLAUDE.md`、`workspace_auv/docs/basic_motion_action.md`（原句"当前仅用于日志"）
并在 `service_action_contract.md` 里写明三档行为。

## 6. 服务/动作字段契约里几条"踩过才知道"的语义

- `/nav/navigate_to` 的 `task_name` 是**逗号分隔的坐标**（`"x,y"` 或 `"x,y,z"`），不是任务名；
  `start` 字段**未使用**（`RunTask` 类型被两个服务端共用而已）。
- 它**无位姿时拒绝规划**，但**响应里看不到原因**（`message='Navigation failed'`），
  真因只在 `navigator` 日志里（`navigate_to rejected: no pose yet on /basic_motion/pose_info …`）。
- `/zit6/update_params`：`json` 优先；**单个数值 = 只改 `kp`**；未知路径/字段静默忽略；
  **永不写回 `sim_pid.yaml`**。
- `/task/exec` **仅 `debug_mode:=true` 可用**，否则一句明确的 message 拒绝。
- `/task/run` 的 `start=false` 与 `/task/stop` 效果相同（前者走 `_run_task_cb` 的 else 分支）。
